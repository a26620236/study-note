### Computer Use Costs 45× More Tokens than Structured APIs
### Computer Use 比結構化 API 多燒 45 倍 token

[原文連結](https://reflex.dev/blog/computer-use-is-45x-more-expensive-than-structured-apis/)

- **Benchmark**
  - Same Claude Sonnet, same admin-panel task (customers, orders, reviews + filtering and pagination).
  - Vision agent: 53 ± 13 steps, ~551k input tokens. API agent: 8 calls, ~12k input tokens.
- **Reliability gap**
  - The vision agent initially failed the task entirely until it was given an explicit numbered walkthrough naming every sidebar item, tab, and form field.
  - That prompt-engineering effort is a hidden cost that doesn't show up in token counts.
- **Takeaway**
  - For internal tools you control, auto-generate APIs from your own code and call them directly — vision/Computer Use is now justifiable mainly when you cannot modify the system being driven.
-------
- **Benchmark**
  - 同一顆 Claude Sonnet、同一個後台任務（客戶、訂單、評論的查詢與分頁）。
  - 視覺 agent：53 ± 13 步，約 55.1 萬 input token。API agent：8 次呼叫，約 1.2 萬 input token。
- **可靠度差距**
  - 視覺 agent 一開始整個任務直接失敗，要把 sidebar、tab、表單欄位通通用編號列出來當步驟才跑得起來。
  - 這段 prompt 工程不會出現在 token 帳單裡，是隱藏成本。
- **結論**
  - 自家內部系統就把 API 自動從程式碼產出來、agent 直接打 API；Computer Use 比較合理的情境只剩下「我沒辦法改那個系統」的時候。

### Anthropic Postmortem on March–April Claude Code Quality Issues
### Anthropic 釋出 3–4 月 Claude Code 品質問題事後報告

[原文連結](https://www.anthropic.com/engineering/april-23-postmortem)

- **Three overlapping issues**
  - Mar 4–Apr 7: default reasoning effort silently dropped from `high` to `medium` to cut latency; users preferred intelligence over speed and it was reverted.
  - Mar 26–Apr 10: a caching bug kept dropping reasoning history every turn instead of once, making Claude "forgetful and repetitive" and burning through usage limits.
  - Apr 16–Apr 20: a system-prompt rule capping inter-tool-call text at 25 words cut coding quality by 3% across models — reverted immediately.
- **Why detection took weeks**
  - Each issue hit a different user segment on staggered timelines, producing the appearance of "broad inconsistent degradation" rather than a single reproducible bug.
- **What users got**
  - Usage-limit resets on Apr 23 for affected subscribers.
  - Anthropic committed to broader testing, stricter prompt-change review, and tighter rollout controls.
-------
- **三個重疊的問題**
  - 3/4–4/7：預設 reasoning effort 偷偷從 `high` 降到 `medium` 想換取低延遲，結果使用者寧可慢一點也要更聰明，已恢復。
  - 3/26–4/10：cache 優化的 bug 讓系統每一輪都把 reasoning history 丟掉一次（應該只丟一次），導致 Claude「健忘又重複」並更快觸頂用量。
  - 4/16–4/20：在 system prompt 加了「兩次 tool call 之間最多 25 字」的規則，三條模型線的 coding 品質都掉了 3%，當天就回滾。

### context-mode: Sandbox Tool Output for Claude Code
### context-mode：把 Claude Code 工具輸出丟進沙箱

[原文連結](https://github.com/mksglu/context-mode)

- **Problem**
  - Tool outputs (Playwright snapshots, large file dumps) blow up the context window and crowd out actual reasoning.
- **Four reduction techniques**
  - Sandboxed execution: only stdout enters context (a 56 KB Playwright snapshot becomes 299 bytes).
  - SQLite + FTS5 indexing: large outputs get indexed, model only sees BM25 search results.
  - Code-first analysis: instead of reading 50 files, agent writes a script that prints just the answer (700 KB → 3.6 KB).
  - Output compression: drops hedging/filler, keeps technical substance — claims 65–75% additional token savings.
- **Six tools**
  - `ctx_execute` (11 languages), `ctx_execute_file`, `ctx_batch_execute`, `ctx_index`, `ctx_search`, `ctx_fetch_and_index` (24h cache).
- **Install**
  - `/plugin marketplace add mksglu/context-mode` then `/plugin install context-mode@context-mode`.
-------
- **問題**
  - 工具輸出（Playwright 快照、大型檔案 dump）很容易把 context window 灌爆，把真正要思考的內容擠掉。
- **四種壓縮手法**
  - 沙箱執行：只有 stdout 進到 context（56 KB 的 Playwright 快照變成 299 bytes）。
  - SQLite + FTS5 索引：大型輸出先進索引，模型只會拿到 BM25 搜尋結果。
  - 程式碼優先：不要讀 50 個檔，叫 agent 寫一段腳本直接 print 答案（700 KB → 3.6 KB）。
  - 輸出壓縮：拿掉模糊詞與廢話，只留技術重點，宣稱再省 65–75% token。
- **六個工具**
  - `ctx_execute`（支援 11 種語言）、`ctx_execute_file`、`ctx_batch_execute`、`ctx_index`、`ctx_search`、`ctx_fetch_and_index`（24 小時快取）。
- **安裝**
  - `/plugin marketplace add mksglu/context-mode` → `/plugin install context-mode@context-mode`。

  - Launch post focuses on the React adapter (`useForm`, `createFormHook`); other framework adapters are in the TanStack ecosystem but not the headline.

  - 內建 `onSubmit`、`onChange`、`onBlur` 驗證；支援欄位組合、陣列欄位的 `pushValue` / `removeValue`，以及用 `useStore` / `Subscribe` 跨欄位讀值。

### CSS `:nth-child(n of <selector>)` for Conditional Form Validation
### 用 CSS `:nth-child(n of <selector>)` 做條件式表單驗證

[原文連結](https://frontendmasters.com/blog/css-n-of-selectors-for-conditional-validation/)

- **What it does**
  - `:nth-child(n of <selector-list>)` counts only the elements matching the inner selector, not all siblings — so you can target the n-th *valid* field, not the n-th DOM child.
- **Concrete use case**
  - Want to show a "ready to submit" message after 3 valid fields? Combine with `:has()` validity checks: `:nth-child(3 of .field:has(input:user-valid))` lights up only when 3 fields are filled correctly.
  - Pure CSS — no JS state machine.
- **Browser status (April 2026)**
  - Firefox renders state-driven styling correctly.
  - WebKit has a current bug where the state-based version doesn't repaint as expected — feature-detect or wait it out before shipping.
-------
- **這語法在做什麼**
  - `:nth-child(n of <selector-list>)` 只在「符合內部選擇器」的元素裡面數，不是在所有兄弟元素裡數——所以你可以指到「第 n 個合法欄位」而不是「第 n 個 DOM 子元素」。
- **實際用法**
  - 想在 3 個欄位都填對之後顯示「可送出」？搭配 `:has()` 檢查 validity：`:nth-child(3 of .field:has(input:user-valid))`，3 個都正確填寫時才會生效。
  - 純 CSS——不用寫 JS 狀態機。
- **瀏覽器狀態（2026 年 4 月）**
  - Firefox 對狀態變化的重繪正常。
  - WebKit 目前有 bug，狀態切換時不會如預期重繪——上 production 前先做 feature detection，或等修好再說。

### Constructable Stylesheets and `adoptedStyleSheets`
### Constructable Stylesheets 與 `adoptedStyleSheets`：每個 shadow root 只解析一次

[原文連結](https://frontendmasters.com/blog/constructable-stylesheets-and-adoptedstylesheets-one-parse-every-shadow-root/)

- **The problem**
  - Each shadow root parsing the same `<style>` block is wasted work — multiplies as web components proliferate.
- **The fix**
  - Build a `CSSStyleSheet` once via `new CSSStyleSheet()`, then attach it to many shadow roots through `shadowRoot.adoptedStyleSheets`.
  - One parse, shared rules, instant updates when you mutate the stylesheet object.
- **When it pays off**
  - Component libraries with many instances of the same component, design-system tokens shared across shadow boundaries, or pages that dynamically inject themed styles.
-------
- **問題**
  - 每個 shadow root 各自解析同一段 `<style>` 是純浪費，元件越多越嚴重。
- **解法**
  - 用 `new CSSStyleSheet()` 建一次，然後把它丟進多個 shadow root 的 `shadowRoot.adoptedStyleSheets`。
  - 解析一次、規則共享、改 stylesheet 物件時所有引用都會立即跟著更新。
- **什麼情況最划算**
  - 同一元件被大量 instance 化的元件庫、跨 shadow 邊界共享的設計系統 token、或是會動態注入主題樣式的頁面。

### Should I Run Plain Docker Compose in Production in 2026?
### 2026 年還能直接用 Docker Compose 跑 production 嗎？

[原文連結](https://distr.sh/blog/running-docker-in-production/)

- **Verdict**
  - Yes — but only if "plain Compose" means Compose plus disciplined operator practices.
- **Tradeoffs**
  - Pro: simplicity, low overhead, no control plane to babysit.
  - Con: no built-in cleanup, self-healing, rolling updates, or image lifecycle management — you have to bring those.
- **Where it fits**
  - Single-node deployments, vendor software shipped to customer environments, internal services that can't justify Kubernetes, edge boxes.
- **Where it doesn't**
  - Multi-node clusters, teams without operational discipline, anywhere you need centralised update orchestration — pay the K8s tax instead.
-------
- **結論**
  - 可以，但前提是「直接用 Compose」其實是「Compose + 有紀律的維運實踐」。
- **取捨**
  - 優點：簡單、overhead 低、沒有 control plane 要照顧。
  - 缺點：沒有內建的清理、自癒、滾動更新或 image 生命週期管理——這些通通要自己補。
- **適合的場景**
  - 單節點部署、賣給客戶端的廠商軟體、規模還撐不起 K8s 的內部服務、邊緣節點。
- **不適合的場景**
  - 多節點叢集、沒有維運紀律的團隊、任何需要中央化更新編排的場景——這些就乖乖去付 K8s 的學習成本。

## Glossary

- **Computer Use / Vision Agent**
  - An agent pattern where the model drives a UI by reading screenshots and emitting clicks/keystrokes, instead of calling an API. Powerful but token-expensive.
  - 一種 agent 模式：模型透過讀截圖、輸出點擊與鍵盤動作來操作 UI，而不是直接呼叫 API。能力強但很燒 token。
- **Reasoning Effort**
  - A dial that controls how much "thinking" the model does before answering. Higher effort = more internal tokens spent on planning, usually slower but smarter.
  - 控制模型回答前要「想多久」的設定。effort 越高代表花在內部規劃的 token 越多，通常較慢但較聰明。
- **Headless Library**
  - A library that handles logic and state but renders nothing — you bring your own JSX/HTML. Trades convenience for full styling control.
  - 只處理邏輯與狀態、完全不負責 UI 渲染的函式庫——JSX/HTML 由你自己寫。犧牲開箱即用、換取完整樣式控制權。
- **Constructable Stylesheets**
  - A browser API that lets you build a `CSSStyleSheet` object in JS once and share it across multiple shadow roots via `adoptedStyleSheets`. Avoids re-parsing the same CSS.
  - 瀏覽器 API：可以在 JS 裡用 `new CSSStyleSheet()` 建一份樣式物件，再透過 `adoptedStyleSheets` 共享給多個 shadow root，避免重複解析同一段 CSS。
- **`:has()` Selector**
  - A CSS selector that matches an element based on its descendants — e.g. `.field:has(input:user-valid)` selects fields containing a valid input. Now widely supported.
  - CSS 選擇器，可以根據後代元素來選父元素——例如 `.field:has(input:user-valid)` 可以選到「裡面有合法 input」的欄位。現在已普及。
- **Release Channel (stable / latest)**
  - A versioning lane. `latest` ships every build immediately; `stable` lags by ~1 week and skips builds with known regressions, trading freshness for reliability.
  - 版本軌道。`latest` 每個 build 立刻發布；`stable` 落後約一週並跳過已知有問題的 build，犧牲新鮮度換取穩定。
- **FTS5 (SQLite Full-Text Search v5)**
  - SQLite's built-in full-text search extension with BM25 ranking. Lets context-mode index large blobs and serve back ranked snippets instead of the whole content.
  - SQLite 內建的全文搜尋擴充（v5），支援 BM25 排序。讓 context-mode 可以把大塊資料先建索引，回答時只回傳相關片段而不是整包內容。
- **MCP Server**
  - A small process that exposes tools (DB queries, API calls, file ops) to an LLM agent over the Model Context Protocol. Adding one expands the agent's capabilities without retraining.
  - 一個小型 process，透過 Model Context Protocol 把工具（資料庫查詢、API 呼叫、檔案操作）開放給 LLM agent 用。加一個就等於擴充 agent 能力，不用重新訓練模型。
