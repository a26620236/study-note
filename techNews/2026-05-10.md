### Cloudflare Dynamic Workflows: Durable Execution Per Tenant, Per Agent
### Cloudflare Dynamic Workflows：每個租戶、每個 Agent 都能跑自己的耐久工作流

[InfoQ 整理](https://www.infoq.com/news/2026/05/cloudflare-dynamic-workflows/)

- **Core**
  - MIT-licensed library that lets workflow code differ at runtime per tenant / agent / request — previously workflow code had to be static per deployment.
  - Built on Cloudflare's Dynamic Workers stack; a Worker Loader routes between the engine and tenant code.
  - Steps are independently retryable; `step.sleep()` and `step.waitForEvent()` hibernate without consuming resources.
- **Why it matters for agents**
  - Agents can author their own execution plans as durable code instead of choosing from pre-baked workflows.
  - Long pauses (e.g. waiting for human approval, external events) cost nothing while idle.
- **Watch**
  - How this composes with Cloudflare Artifacts — together they form a durable + auditable agent runtime.
-------
- **核心**
  - MIT 授權的 library，工作流程式碼可在 runtime 依租戶／agent／請求變動 — 過去同一份部署只能跑一份固定程式碼。
  - 建在 Cloudflare 的 Dynamic Workers 之上；Worker Loader 負責在引擎與租戶程式碼之間路由。
  - 每個 step 可獨立重試；`step.sleep()` 與 `step.waitForEvent()` 可無成本休眠。
- **對 agent 的意義**
  - Agent 可以自己寫執行計畫做成耐久程式碼，不必從預先寫好的工作流挑一個。
  - 長時間暫停（等人類核准、等外部事件）期間不耗資源。
- **觀察**
  - 與 Cloudflare Artifacts 怎麼搭 — 兩者合起來就是一套耐久且可稽核的 agent runtime。

### OpenAI Adds WebSocket Execution Mode to the Responses API — 40% Less Latency
### OpenAI Responses API 改用 WebSocket，延遲降 40%

[InfoQ 整理](https://www.infoq.com/news/2026/05/openai-websocket-responses-api/)

- **Core**
  - Replaces HTTP request/response per agent step with a persistent, bidirectional connection — no repeated handshakes, no connection setup overhead.
  - Sustained ~1,000 TPS with bursts to 4,000 TPS in production.
- **Real-world results**
  - Vercel: 40% latency cut. Cline (multi-file workflows): 39%. Cursor: 30%.
- **Pattern**
  - Pre-warm sessions by pre-sending system prompts and tool definitions when the connection opens.
  - Best fit for incremental code generation and orchestrated multi-step agent workflows.
-------
- **核心**
  - 過去 agent 的每一步都是一次 HTTP request/response；新模式改用持久雙向連線，不再重複握手與建連。
  - 生產實測穩態 ~1,000 TPS，尖峰可衝到 4,000 TPS。
- **實測效果**
  - Vercel 延遲降 40%、Cline（多檔工作流）降 39%、Cursor 降 30%。
- **使用模式**
  - 連線一開就先送 system prompt 和工具定義「預熱」session。
  - 最適合用在串流式程式生成與多步驟 agent 編排。

### GitHub's Defense-in-Depth Model for Agentic CI/CD
### GitHub 公開 agentic CI/CD 的 defense-in-depth 模型

[InfoQ 整理](https://www.infoq.com/news/2026/05/github-agentic-workflows/)

- **Four pillars**
  - **Isolation**: ephemeral sandboxed containers, restricted permissions, narrow network access.
  - **Constrained execution**: writes disabled by default; changes flow through PRs, not direct commits.
  - **Secret protection**: credentials served via trusted proxies outside the agent boundary, blocking prompt-injection exfiltration.
  - **Observability**: logging across trust boundaries — network, model interactions, sensitive runtime actions.
- **Threat model**
  - Prompt injection from untrusted inputs, privilege escalation, data exfiltration, non-deterministic side effects.
- **Take this seriously if**
  - You let an agent merge, deploy, or touch secrets in CI — the four pillars are a useful checklist for your own pipeline.
-------
- **四大支柱**
  - **隔離**：短命的沙盒 container、最小權限、限制網路出口。
  - **受限執行**：寫操作預設關閉，所有變更透過 PR 而非直接 commit。
  - **Secret 保護**：憑證放在 agent 邊界外的可信代理，擋掉 prompt injection 偷 secret 的路徑。
  - **觀測**：跨信任邊界記錄網路、模型互動、敏感 runtime 行為。
- **威脅模型**
  - 不可信輸入導致的 prompt injection、權限升級、資料外洩、非決定性副作用。
- **誰該認真看**
  - 你已經讓 agent 在 CI 裡合併、部署、碰 secret 的話 — 這四項可直接當自己 pipeline 的 checklist。

### Builder.io: Agent-Native Architecture and the Quality Debt It Creates
### Builder.io：Agent-Native 架構與它帶來的「品質負債」

[Agent-Native](https://www.builder.io/blog/agent-native-architecture) | [Quality Debt](https://www.builder.io/blog/agent-productivity-is-creating-a-quality-debt)

- **Three stages of "AI" software**
  - AI-enabled (works without AI) → AI-native (collapses without AI) → Agent-native (humans and agents share full-feature parity).
- **Five design principles for agent-native**
  - Agent UI parity, unified action model, shared state and context, protocol-ready (MCP / A2A), governed execution under same permissions as humans.
- **The quality debt**
  - Agents now write PRs faster than reviewers and tests can validate them — bottleneck shifted from *writing* to *validating that the product works*.
  - Code review and unit tests no longer catch behavioral regressions; you need an agent that opens the actual product and walks through flows.
-------
- **「AI」軟體的三階段**
  - AI-enabled（沒 AI 也能跑）→ AI-native（沒 AI 就掛）→ Agent-native（人類與 agent 共享同一套全功能介面）。
- **Agent-native 的五個設計原則**
  - UI 對等、統一動作模型、共享狀態與上下文、Protocol 就緒（MCP／A2A）、治理執行（與人類同一套權限與稽核）。
- **品質負債**
  - Agent 寫 PR 已經比 reviewer 跟測試能驗證的速度還快 — 瓶頸從「寫程式」變成「驗證產品真的能用」。
  - Code review 與 unit test 不再能擋住行為層回歸；需要一個會自己開產品、跑使用流程的 agent。

### Local-First Web Architecture: When It Works and When It Doesn't (Smashing)
### Local-First Web 架構在 2026 的真實樣貌（Smashing 週末長文）

[原文連結](https://www.smashingmagazine.com/2026/05/architecture-local-first-web-development/)

- **What it actually is**
  - Local-first ≠ offline-first ≠ PWA. It's a *data architecture* — the user's device holds the primary copy of their data.
- **2026 stack the author recommends**
  - UI: React with local SQLite queries.
  - Client DB: SQLite via WebAssembly (`wa-sqlite`) persisted to OPFS.
  - Sync: PowerSync (mature) or ElectricSQL (more ambitious).
  - Conflicts: last-write-wins per field; server validates domain invariants.
  - Real-time collab: Yjs only when needed.
- **When to skip it**
  - Server-generated data (analytics dashboards), strong-consistency systems (banking, inventory), or simple CRUD without offline / collab needs.
- **Gotcha**
  - Initial sync is the perf bottleneck; local reads/writes are instantaneous.
-------
- **它到底是什麼**
  - Local-first ≠ offline-first ≠ PWA。它是一種「資料架構」 — 使用者裝置是資料的主拷貝。
- **作者推薦的 2026 技術棧**
  - UI：React 配本地 SQLite query。
  - 客戶端資料庫：SQLite over WebAssembly（`wa-sqlite`）持久化到 OPFS。
  - 同步引擎：PowerSync（成熟）或 ElectricSQL（前衛）。
  - 衝突解決：欄位級 last-write-wins，server 端驗領域不變條件。
  - 即時協作：只有需要時才用 Yjs。
- **什麼情況不該用**
  - 伺服器生成的資料（analytics dashboard）、需強一致性的系統（銀行、庫存）、不需要離線或協作的簡單 CRUD。
- **要小心**
  - 初次同步是效能瓶頸；本地讀寫本身是即時的。

### Figma Builds FigCache — In-House Redis Proxy for Six-Nines Uptime
### Figma 自製 FigCache — 為了六個 9 可用性自己寫 Redis Proxy

[InfoQ 整理](https://www.infoq.com/news/2026/05/figma-redis-figcache/)

- **Why build, not buy**
  - Open-source proxies lacked semantic awareness — couldn't extract full annotated arguments from arbitrary Redis commands, blocking custom safeguards.
- **What it solves**
  - Connection counts hitting hard limits, thundering-herd reconnects saturating Redis I/O, fragmented client libraries with inconsistent observability, multi-shard CROSSSLOT errors handled internally via scatter-gather.
  - Unified observability cut incident diagnosis from hours to minutes.
- **Architecture**
  - Stateless service on a Go RPC framework (ResPC) over Redis Serialization Protocol.
  - Front/back layer split; routing rules use Starlark evaluated at runtime — config changes without redeploy.
-------
- **為什麼自己寫不買現成的**
  - 開源 proxy 缺乏語意感知 — 無法從任意 Redis 命令中抽出完整帶標註的引數，因此沒辦法做客製化保護。
- **解了什麼問題**
  - 連線數逼近硬上限、湧入式重連塞爆 Redis I/O、客戶端 library 分散導致觀測性不一致、多 shard pipeline 的 CROSSSLOT 錯誤改由 proxy 內部 scatter-gather 處理。
  - 統一觀測讓事故診斷時間從「以小時計」縮到「以分鐘計」。
- **架構**
  - 無狀態服務，建在 Go RPC 框架（ResPC）之上、走 Redis 序列化協議。
  - 前後端分層；路由規則用 Starlark 在 runtime 評估 — 改設定不必重新部署。

## Glossary

- **Durable execution**
  - A workflow execution model where each step is independently retryable and the workflow's state survives restarts and long pauses without consuming resources.
  - 工作流的執行模型，每個 step 可獨立重試、狀態能在重啟與長暫停期間留存且不耗資源。
- **MCP server**
  - A server that exposes tools and resources to LLM agents over the Model Context Protocol — the standardized way agents call external systems.
  - 透過 Model Context Protocol 把工具與資源暴露給 LLM agent 的伺服器，是 agent 呼叫外部系統的標準介面。
- **gVisor**
  - A user-space kernel from Google that provides syscall-level isolation for containers — used here to safely run untrusted agent code.
  - Google 的 user-space kernel，在 syscall 層做容器隔離 — 這裡用來安全執行不可信的 agent 程式碼。
- **Hypercluster**
  - A single Kubernetes control plane stretched across multiple regions and managing very large accelerator (GPU/TPU) fleets as one logical cluster.
  - 單一 Kubernetes 控制平面跨多個區域，把超大 GPU/TPU 機隊當成一個邏輯叢集管理。
- **KV cache tiering**
  - Spreading the LLM's key-value attention cache across RAM, local SSD, and remote storage based on access frequency to extend effective cache size.
  - 依存取頻率把 LLM 的 KV attention cache 分層存放於 RAM、本地 SSD、遠端儲存，藉此擴大有效快取容量。
- **A2A (agent-to-agent)**
  - A class of protocols for agents to discover and call other agents, beyond calling pre-defined tools.
  - Agent 之間互相發現、互相呼叫的協議類別，補足「只能呼叫預先定義工具」的限制。
- **OPFS (Origin Private File System)**
  - A browser-provided private filesystem scoped to an origin — used by `wa-sqlite` to persist a real SQLite database in the browser.
  - 瀏覽器提供、以 origin 為單位的私有檔案系統 — `wa-sqlite` 用它在瀏覽器中持久化真正的 SQLite 資料庫。
- **CROSSSLOT error**
  - A Redis Cluster error that occurs when a single command touches keys in different hash slots, breaking the per-slot routing assumption.
  - Redis Cluster 中當單一指令觸及不同 hash slot 的 key 時拋出的錯誤，違反了每個 slot 各自路由的假設。
- **Scatter-gather**
  - A pattern that splits one logical request into many sub-requests sent to different backends, then merges the results — used here to handle multi-shard pipelines.
  - 把一個邏輯請求拆成多個子請求送往不同後端，再合併結果的模式 — 這裡用來處理多 shard 的 pipeline。
- **shadcn/ui**
  - A copy-paste component pattern (not a package) for React + Tailwind apps, where you own the source of every component you install from the registry.
  - React + Tailwind 應用的「複製貼上」元件模式（不是 npm 套件），你從 registry 安裝的每個元件原始碼都歸你所有並可自行修改。
