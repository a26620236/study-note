### Nolan Lawson: Using AI to Write Better Code More Slowly
### Nolan Lawson：用 AI 來「慢慢寫出更好的程式」

[原文連結](https://nolanlawson.com)

- **Thesis**
  - LLMs can be used deliberately to *raise* code quality — not just to ship faster. The slow-down is the feature.
- **Concrete workflow**
  - Run multiple agents on the same PR ranked by severity: "Run a Claude sub-agent, Codex, and Cursor Bugbot to find bugs in this PR ranked by critical/high/medium/low."
  - Iterate: fix criticals, skip nits. Often surfaces *pre-existing* bugs as side-quests.
- **Recommendations**
  - Multi-model validation reduces false positives.
  - Ask for Markdown / Mermaid documentation alongside changes.
  - Read and understand every PR before merge — independent of who/what wrote it.
  - Optimise for code health over raw productivity metrics.
-------
- **論點**
  - LLM 可以「刻意慢用」來「提升」程式碼品質 — 不是只能拿來衝速度。「慢」本身就是它的好處。
- **具體工作流**
  - 同一個 PR 同時跑多個 agent，依嚴重度排序：「跑 Claude sub-agent、Codex、Cursor Bugbot 找這個 PR 的 bug，按 critical／high／medium／low 排」。
  - 反覆：先修 critical、放掉小瑕疵。常常會順便挖出本來就存在的 bug。
- **建議**
  - 多模型互相驗證，可降低 false positive。
  - 改動之餘要求 Markdown／Mermaid 文件。
  - 不論誰寫的 PR，merge 前都要讀懂。
  - 用「程式碼健康度」當目標，而非「產出量」。

### Your Node.js Streams Aren't Backpressuring — They're Silently Eating Memory
### 你的 Node.js stream 沒做 backpressure — 它正悄悄吃光記憶體

[原文連結](https://frontendmasters.com/blog/your-node-js-streams-arent-backpressuring-theyre-silently-eating-your-memory/)

- **The symptom**
  - Pods climb to ~3.8GB and get OOM-killed. Code passes review and integration tests because the leak only shows under load.
- **The root cause**
  - Devs ignore the boolean return value from `.write()`. `highWaterMark` is *advisory*, not a hard limit — Node buffers unbounded if you keep calling `.write()` after it returns `false`.
- **The fix pattern**
  - ```js
    for await (const row of cursor) {
      const ok = writable.write(csv);
      if (!ok) await once(writable, "drain");
    }
    ```
- **Hidden traps**
  - `.pipe()` doesn't propagate errors — use `pipeline()` from `node:stream/promises`.
  - `async/await` paces reads but not writes — backpressure still required.
  - Node 22 raised default `highWaterMark` 16KB → 64KB, so the bug hides longer.
  - Transform streams have independent buffers on each side — memory growth easy to miss.
  - Honouring backpressure can expose downstream DB connection-pool starvation.
-------
- **症狀**
  - Pod 慢慢漲到 ~3.8GB 後被 OOM 砍掉。code review 與 integration test 都過 — 因為只有在 load 下才會洩漏。
- **根因**
  - 程式碼忽略 `.write()` 的 boolean 回傳值。`highWaterMark` 只是「建議」、不是硬上限 — 一旦 `.write()` 回 `false` 還繼續呼叫，Node 就會無上限地 buffer。
- **修補模式**
  - ```js
    for await (const row of cursor) {
      const ok = writable.write(csv);
      if (!ok) await once(writable, "drain");
    }
    ```
- **隱藏陷阱**
  - `.pipe()` 不會傳遞錯誤 — 改用 `node:stream/promises` 的 `pipeline()`。
  - `async/await` 控制了讀的速度但沒控寫的速度 — backpressure 還是要做。
  - Node 22 預設 `highWaterMark` 從 16KB 拉到 64KB，bug 會更晚才暴露。
  - Transform stream 兩側各自有 buffer — 記憶體成長很容易被忽略。
  - 正確做 backpressure 後，可能反過來暴露下游 DB connection pool 不夠用。

### Better Browser Caching with `No-Vary-Search`
### 用 `No-Vary-Search` 改進瀏覽器快取

[原文連結](https://frontendmasters.com/blog/better-browser-caching-with-no-vary-search/)

- **What it is**
  - An HTTP response header that tells the browser *which* query parameters affect the response body — so it knows when two URLs are "the same page" for caching purposes.
- **The problem it solves**
  - Today `?product_id=7` and `?utm_source=newsletter` both fragment the cache; the browser can't tell that UTM tags don't change content.
  - With `No-Vary-Search`, the server says "ignore `utm_*` for cache identity" — UTM-tagged URLs hit the same cached page.
- **Typical use**
  - Pair with a list of known tracking params to keep their URLs single-cached.
  - Especially useful where prefetch / prerender hints exist — fewer unique URLs means more hits.
-------
- **是什麼**
  - 一個 HTTP 回應 header，告訴瀏覽器「哪些 query 參數真的影響回應內容」 — 讓瀏覽器判斷兩個 URL 在快取意義上是不是同一頁。
- **解決什麼問題**
  - 現況：`?product_id=7` 與 `?utm_source=newsletter` 都會把快取切碎；瀏覽器無法分辨 UTM 不影響內容。
  - 有了 `No-Vary-Search`，server 可以宣告「`utm_*` 不影響快取身分」 — 帶 UTM 的 URL 命中同一份快取。
- **典型用法**
  - 列出已知的追蹤參數一次告訴瀏覽器，讓這些參數帶的 URL 共用同一份快取。
  - 與 prefetch／prerender 提示搭起來效果更明顯 — 唯一 URL 越少，命中率越高。

### `gobee`: Write eBPF Programs in Go Instead of C
### `gobee`：用 Go（而非 C）寫 eBPF 程式

[GitHub 連結](https://github.com/boratanrikulu/gobee)

- **How it works**
  - Transpiles a strict subset of Go into BPF C, then leans on clang's mature backend.
  - `gobee translate` produces BPF C, source maps, and typed `cilium/ebpf` bindings.
  - Userspace Go loads via those bindings — single language, both sides.
- **Developer experience wins**
  - Typed map bindings — no more stringly-typed lookups.
  - Verifier errors map back to **Go file:line:col**, not raw C.
  - Built-in `bpfvet` kernel-version checks fail fast instead of cryptic `EINVAL`.
- **Position vs alternatives**
  - C + `bpf2go`: full helper coverage, but C ergonomics. Aya (Rust): same idea in Rust.
  - `gobee`: ~200 typed wrappers; not a wholesale libbpf replacement — targets projects wanting a unified Go workflow.
-------
- **怎麼運作**
  - 把 Go 的嚴格子集轉譯為 BPF C，再走 clang 成熟的 backend。
  - `gobee translate` 產生 BPF C、source map、type-safe 的 `cilium/ebpf` binding。
  - Userspace Go 用這些 binding 載入 — 兩側都是同一語言。
- **DX 改善**
  - Map 有型別 binding — 不再用字串型 lookup。
  - Verifier 錯誤訊息會對應回 **Go 檔名:行:欄**，而不是 raw C。
  - 內建 `bpfvet` 做 kernel 版本檢查，遇到不相容會快速失敗，不會丟出費解的 `EINVAL`。
- **與替代方案的定位**
  - C + `bpf2go`：helper 覆蓋完整，但 C 的 DX 不友善。Aya（Rust）：同樣理念，換成 Rust。
  - `gobee`：約 200 個 typed wrapper；不是要取代 libbpf — 鎖定「整套 Go workflow」這類專案。

## Glossary

- **Backpressure (Node.js streams)**
  - The mechanism by which a writable stream signals "stop sending me data" by returning `false` from `.write()` — ignoring it lets internal buffers grow without bound.
  - Writable stream 透過 `.write()` 回傳 `false` 來告訴生產端「停！別再丟資料給我」的機制 — 忽略它的後果是內部 buffer 無上限地長大。
- **`highWaterMark` (Node.js)**
  - The advisory threshold that decides when a stream signals backpressure — but only by *returning false*; it never blocks the write. Treat as a hint, not a limit.
  - Stream 用來決定何時觸發 backpressure 訊號的「建議閾值」 — 它只透過回傳 `false` 表達，不會擋下寫入。當作提示而非上限。
- **No-Vary-Search**
  - An HTTP response header that declares which URL query parameters do *not* affect response content — letting the browser unify cached entries that only differ in tracking params.
  - 一個 HTTP 回應 header，宣告哪些 URL query 參數「不會影響內容」 — 讓瀏覽器把只差在追蹤參數的 URL 視為同一份快取。
- **Knowledge graph (of code)**
  - A graph representation of a codebase where nodes are functions / classes / files and edges are calls / imports / inheritance — queryable in ways that file-scan can't match.
  - 把 codebase 表示成圖：節點是函式／類別／檔案，邊是呼叫／import／繼承 — 可做檔案掃描做不到的查詢。
- **MITRE ATT&CK**
  - A widely-used knowledge base of real-world adversary tactics and techniques across the cyber kill chain — the lingua franca of threat hunting.
  - 一份廣泛使用的「現實攻擊方戰術與技巧」知識庫，覆蓋網路殺鏈 — 威脅獵捕的通用語言。
- **MITRE ATLAS**
  - The same idea as ATT&CK but for adversarial threats targeting AI/ML systems — relevant as agents become attack surfaces.
  - 與 ATT&CK 同概念，但專門對應 AI／ML 系統會碰到的對抗威脅 — agent 變成攻擊面後愈來愈重要。
- **eBPF**
  - A Linux kernel technology for safely running sandboxed programs in kernel context — used for observability, security, and networking without writing kernel modules.
  - Linux kernel 技術，可在 kernel context 安全地執行被沙盒過的程式 — 用於觀測、資安、網路，不必寫 kernel module。
- **BPF verifier**
  - The Linux kernel component that statically checks every BPF program before loading — prevents kernel crashes but produces notoriously hard-to-read errors.
  - Linux kernel 在載入 BPF 程式前做靜態檢查的元件 — 可避免 kernel crash，但錯誤訊息出名地難讀。
